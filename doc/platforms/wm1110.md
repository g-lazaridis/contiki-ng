# wm1110-dk: Seeed Wio-WM1110 Development Kit (LoRa)

A board for the `nrf52840` platform that adds a Semtech **LR1110** sub-GHz
transceiver, allowing Contiki-NG's 6LoWPAN/RPL/TSCH stack to run over LoRa
instead of IEEE 802.15.4.

The [Wio-WM1110](https://wiki.seeedstudio.com/wio_wm1110_dev_kit/) module
combines an nRF52840 host MCU with an LR1110, connected over SPI. Because the
nRF52840 is already supported upstream, this board reuses the existing CPU port
and adds the board definition and the radio.

See [the top-level README](../../README.md) for the TSCH and Orchestra changes
that make LoRa workable, and
[`examples/wm1110/`](../../examples/wm1110/README.md) for the examples.

## Port features

Supported:

* LoRa PHY via the LR1110, integrated as a Contiki-NG `NETSTACK_RADIO`
* TSCH with a 750 ms timeslot, and RPL/6LoWPAN above it
* Receive timestamping accurate enough for TSCH synchronisation, using the
  nRF52840's PPI (see below)
* LR1110 firmware update from a compiled-in image
* Serial console over the USB-C port
* User LEDs and buttons
* GPIO tracing of TSCH timeslot events for logic-analyser capture

Not supported:

* The 2.4 GHz IEEE 802.15.4 radio in the nRF52840 is not used on this board
  (`PLATFORM_HAS_RADIO 0`); the LR1110 is the netstack radio
* Multi-channel TSCH — the band leaves no room for a second channel
* CCA / channel activity detection
* The kit's SHT41 temperature/humidity sensor and LIS3DHTR accelerometer are
  not driven; only the nRF's internal temperature sensor is registered
* GNSS and Wi-Fi scanning, which the LR1110 supports and the vendored Semtech
  driver exposes, but which nothing in this port uses
* BLE, as with the rest of the nRF52840 port

## Prerequisites

The same ARM toolchain as any other nRF52840 target — see
[the nRF52840 guide](nrf52840.md) and
[the toolchain instructions](../getting-started/Toolchain-installation-on-Linux.md).

### Flashing

The kit brings the nRF52840's SWD lines out to pads and carries no on-board
debugger, so programming it needs an external probe wired to SWDIO, SWCLK,
GND and a voltage reference.

The `.upload` targets inherited from the nRF52840 port invoke `nrfjprog`,
which drives SEGGER J-Link hardware only. With any other probe, use the
`.openocd-upload` target and name the probe:

```bash
make TARGET=nrf52840 BOARD=wm1110-dk OPENOCD_INTERFACE=stlink-dap \
     node.openocd-upload
```

| `OPENOCD_INTERFACE` | Probe |
|---------------------|-------|
| `cmsis-dap` | CMSIS-DAP / DAPLink, including the Raspberry Pi Debug Probe |
| `stlink-dap` | ST-Link driven as a plain DAP; needs firmware V2J28 or newer |
| `stlink` | ST-Link as a high-level adapter, for older firmware |
| `jlink` | SEGGER probes, as an alternative to `nrfjprog` |

This route also needs one tool fewer: the `nrfjprog` targets build a merged
Intel hex with `srec_cat` from the `srecord` package, whereas OpenOCD reads
the ELF directly.

Another Nordic DK or a BBC micro:bit can also act as the probe over SWD,
since both carry a J-Link OB.

#### APPROTECT

An nRF52840 with read-back protection engaged must have it cleared through
the CTRL-AP before it will accept a new image; OpenOCD reports the device as
locked. Only a probe driven as a real DAP can do this, which for an ST-Link
means `stlink-dap` and firmware V2J28 or newer — the `stlink` high-level mode
cannot reach the CTRL-AP. A board that has never been locked is unaffected.

### Linking with a recent toolchain

Contiki-NG passes `-Wl,--fatal-warnings` when `WERROR=1`, which is the
default. Newer newlib releases (4.6 and later, as shipped with GCC 14+) warn
that the `nosys`/`nano` syscall stubs are unimplemented:

```
warning: _close is not implemented and will always fail
```

Those warnings are expected on a bare-metal target with no filesystem, but
`--fatal-warnings` turns them into a link failure. Relax just the linker and
keep `-Werror` on the compiler:

```bash
make TARGET=nrf52840 BOARD=wm1110-dk LDFLAGS_WERROR=
```

This is not specific to this board or to LoRa: every nRF52840 target,
including the stock DK and Dongle examples, fails the same way on such a
toolchain. Building inside the project's Docker image avoids it, since that
image pins GCC 10.

## Building

Select the board with `BOARD=wm1110-dk`:

```bash
cd examples/wm1110/hello-world
make TARGET=nrf52840 BOARD=wm1110-dk hello-world.upload
```

## Pin map

Connections between the nRF52840 and the LR1110 inside the WM1110 module, as
defined in `nrf52840-board-def.h`:

| Signal | nRF52840 pin |
|--------|--------------|
| LR1110 `NRESET` | P1.10 |
| LR1110 `BUSY` | P1.11 |
| SPI `CS` | P1.12 |
| SPI `SCK` | P1.13 |
| SPI `MOSI` | P1.14 |
| SPI `MISO` | P1.15 |
| LR1110 `IRQ` | P1.08 |

SPI runs on SPIM instance 3 at 8 MHz, mode 0, MSB first.

## Receive timestamping

TSCH keeps nodes synchronised using the timestamp of the received frame, so its
accuracy sets the guard time the network needs. Reading a timestamp in software
from an interrupt handler is too jittery at these timescales.

Instead the port uses the nRF52840's **PPI**, which connects peripheral events
to peripheral tasks directly in hardware, without the CPU:

1. The LR1110 is configured via `SetDioIrqParams` to raise its IRQ pin on
   preamble detection.
2. That pin is P1.08 on the nRF.
3. A PPI channel links the *pin change event* to a *timer clear task*. The
   timer starts when the radio is turned on and is cleared the instant a
   preamble arrives, with no software in the path.
4. When the driver reads the frame, it reads the timer and derives the absolute
   timestamp.

Measured over 1000 timeslots, a node's timeslot start sits roughly 1 ms from
its router's.

## Radio off during a timeslot

`TSCH_CONF_RADIO_ON_DURING_TIMESLOT` is disabled, so the LR1110 is powered down
between the transmit and receive phases of a slot rather than left listening.
That saves a meaningful amount of energy over a 750 ms slot, but the transceiver
then needs time to come back up — which is why the timeslot offsets in
`lr11xx-tsch-timing.c` are more relaxed than a 2.4 GHz radio would need.

## Debugging TSCH

Logging over serial from inside a timeslot desynchronises the node from its
time source, so it is not usable for debugging slot behaviour. Instead, define
`WM1110_CONF_TSCH_DEBUG_GPIO` in your `project-conf.h` and include
`wm1110-tsch-debug.h`:

| Pin | Meaning |
|-----|---------|
| P0.19 | High for the duration of every timeslot |
| P0.20 | Toggles at each stage of a reception slot |
| P0.21 | Toggles at each stage of a transmission slot |

Capturing these with a logic analyser on two boards side by side shows the
offset between a router's slot and a node's directly. This is how the timeslot
timings were arrived at.

## Updating the LR1110 firmware

The radio driver is developed against LR1110 transceiver firmware 04.01. Check
what a board is running with the `lr11xx-version` example; if it is older,
flash a newer image with the `firmware-update` example, which carries images
04.01, 03.08 and 03.07 as compiled-in C arrays.
